# План збірки

Початкові кроки 1–5 нижче виконані. Наступна версія планується в розділі «Версія 2» наприкінці документа; реалізація ще не починалася.

Після кожного кроку оновлювати `PROGRESS.md` і робити коміт із коротким описом українською. Після змін в обліку обов’язково запускати `uv run bean-check main.beancount` і показувати результат; перевірка має пройти без повідомлень. Усі Python-команди виконувати через `uv run`, нових пакетів без дозволу не встановлювати. `data/` не змінювати.

## 1. Підготувати рахунки та правила категорій

**Зробити**
- Створити `main.beancount` для Beancount 3: валюта PLN, відкриття всіх рахунків із розділу «Проєкт» у `AGENT.md`, початкові 4 500 PLN на 31.07.2026 через рахунок початкового капіталу, включення `transactions.beancount`. Створити порожній файл операцій для початкової перевірки.
- Доповнити `rules.csv`: Play — телефон і фіксована витрата; Rossmann — косметика та побутова хімія; Decathlon — спорт. Перевірити відповідність опису зарплати правилу доходу. Зберегти три окремі категорії їжі та порядок Bolt Food перед Bolt; фіксованість операцій надалі позначати `#fixed`.

**Перевірити**
- Прочитати виписку без зміни її вмісту: формат, дати, валюта, стан операцій, комісії та відповідність початкового залишку. Якщо є непідтримувані значення, спочатку визначити їх обробку за фактичними даними.
- Зіставити приклади з правилами: Bolt Food і Wolt — доставка, Bolt і Uber — транспорт без `#fixed`, ZTM — транспорт із `#fixed`, Play — телефон із `#fixed`.
- Запустити `uv run bean-check main.beancount`; переконатися, що всі використані рахунки відкриті, початковий залишок не записаний як дохід.

## 2. Імпортувати виписки

**Зробити**
- Створити `import.py`: читати всі CSV у `data/`, застосовувати перше правило без урахування регістру, записувати операції з датою завершення в `transactions.beancount`. Для невідомих витрат використовувати `Expenses:Без-Категорії`, для надходжень без правила доходу — `Income:Інше`.
- Уникати дублів за ключем «дата завершення, опис, сума, залишок». Генерувати файл заново при кожному запуску; не редагувати його вручну. Для перевірки банківського залишку зберігати порядок рядків у виписці.
- Перевіряти коректність вхідних даних; помилки пояснювати з посиланням на файл і рядок. Не залишати частково перезаписаний файл операцій після помилки.

**Перевірити**
- Запустити `uv run python import.py`, потім `uv run bean-check main.beancount` без повідомлень.
- Звірити кількість унікальних операцій, суми надходжень і списань, кінцевий залишок із CSV. Перевірити, що нетиповий порядок часу всередині дня не порушує звірку.
- Повторити імпорт: результат не змінюється. На тимчасових копіях поза `data/` перевірити дубль рядка, невідомий опис та помилкову суму; вихідні виписки не змінювати.

## 3. Розрахувати місячні підсумки

**Зробити**
- Додати збережені запити нативною директивою `query`: витрати за категоріями й календарними місяцями; доходи, витрати та заощадження; витрати з тегом `#fixed` і без нього.
- Норму заощаджень рахувати як `(дохід − витрати) / дохід × 100%`; частки фіксованих і керованих витрат — від усіх витрат. Виводити витрати й доходи у зрозумілих додатних сумах, зберігаючи знак різниці заощаджень.

**Перевірити**
- Запустити `uv run bean-check main.beancount` і виконати запити через `uv run bean-query`.
- Незалежно звірити місячні підсумки з CSV: сума категорій дорівнює витратам; фіксовані плюс керовані дорівнюють витратам; дохід мінус витрати дорівнює заощадженням. Початкові 4 500 PLN не впливають на дохід.
- Перевірити від’ємні заощадження, нульовий дохід і нульові витрати на тимчасових даних поза `data/`; не ділити на нуль.

## 4. Згенерувати короткий HTML-звіт

- Обійтися без нових пакетів, зовнішніх ресурсів і переходів до операцій; при помилці обліку не створювати новий звіт.

- Звірити цифри зі запитами; перевірити позначку жовтня, відсутність прогнозу, читабельність і роботу без інтернету.
- Перевірити відмову генерації при помилці обліку та зрозумілий вивід для нульових знаменників.

## Версія 2 — Оля, Марко та спільний бюджет

### Результат і межі

Розширити наявний трекер протягом 12 тижнів, працюючи кілька вечорів на тиждень. Зберегти Python, Beancount, правила категорій та оформлення звіту. Додати три вкладки, другий формат CSV і введення витрат із телефона. Користувачів рівно двоє; публічна реєстрація, застосунки для сторів, банківські API та інтеграції моделей у цю версію не входять.

Зараз результат — статичний HTML. Для спільного збереження даних із двох телефонів додати невеликий серверний шар до цього проєкту. Браузерний інтерфейс використовує наявні розрахунки, а не окрему копію обліку. Конкретний хостинг і потрібні пакети визначити на етапі технічної перевірки; цей план не встановлює пакети й не публікує фінансові дані.

### Три вкладки

| Вкладка | Що показує за обраний місяць |
| --- | --- |
| Загальна | Сумарні доходи, витрати й заощадження обох; категорії; окремий блок спільних оренди й продуктів: загальна сума, половина кожного, хто фактично оплатив, хто кому має компенсувати |
| Оля | Її дохід, особисті витрати плюс її частка спільних, заощадження, фіксовані та змінні витрати; окремо фактичні оплати й сума взаєморозрахунків |
| Марко | Такі самі показники для Марка; поки його дані не додано — повідомлення «Даних ще немає», без вигаданих нулів |

Вибір місяця спільний для вкладок. Кнопка «Додати витрату» доступна на телефоні. Форма: дата, сума PLN, опис, категорія, хто оплатив, особиста чи спільна. Для оренди й продуктів пропонувати 50/50 із можливістю позначити особисту покупку; решта за замовчуванням особиста. Пропонована модель доступу: два окремі входи в один бюджет із доступом до всіх трьох вкладок; видимість особистих деталей підтвердити до відкриття доступу.

### Правила обліку

- Розрізняти платника та того, на кого припадає витрата. Спільну покупку показувати один раз у загальних витратах і по половині у персональних вкладках. Наприклад, Оля оплатила продукти на 100 PLN: загальні витрати 100 PLN, частка кожного 50 PLN, Марко має компенсувати Олі 50 PLN.
- Компенсація між ними зменшує борг, але не створює нового доходу чи витрати. Заощадження у персональній вкладці рахувати після розподілу спільних витрат; фактичну зміну банківського залишку показувати й звіряти окремо.
- Для непарної кількості грошів встановити один стабільний порядок округлення: частка Олі округлюється до гроша, частка Марка дорівнює залишку. Сума часток завжди дорівнює покупці.
- Дата переходу на спільний облік задається явно. Серпень і вересень Олі залишаються історією старої версії: змінні витрати 2 195,21 та 2 582,42 PLN. Не перерозподіляти їх заднім числом без підтвердження складу спільних покупок.
- Рахунки банків, власник, джерело й ідентифікатор операції зберігаються окремо. Однакові суми й описи в різних банках не є підставою видаляти операцію як дубль.
- Ручні записи зберігаються окремо від згенерованого файла операцій, щоб імпорт їх не стирав. При появі відповідного рядка CSV запропонувати зіставлення; після підтвердження це одна витрата з двома джерелами. Сумнівні збіги не об’єднувати автоматично.
- Дата покриття й початок обліку задаються для кожного користувача. Якщо дані одного неповні, загальний звіт явно неповний. Початковий залишок Марка брати з його виписки, не копіювати залишок Олі.
- Для двох одночасних записів передбачити безпечне збереження без втрати змін; повторне натискання «Зберегти» не створює другу витрату.

### Бюджет і перевірка окупності

Ліміти нижче — розподіл доступних $200, а не перевірені ціни постачальників. Перед вибором сервісу перевірити актуальну річну вартість із податками, продовженням і можливими доплатами.

| --- | ---: |
| Сервер і збереження даних | $100 |
| Домен, лише якщо потрібен | $20 |

Якщо платний інструмент розробки купується саме для цього трекера, його вартість теж входить у $200. Не спиратися на тимчасовий безплатний період як на річний кошторис. Власний час не є грошовим платежем, але обмежує обсяг робіт кількома вечорами на тиждень.

Середні історичні змінні витрати Олі: (2 195,21 + 2 582,42) / 2 = 2 388,815 PLN на місяць. Це орієнтир, а не доказ майбутньої економії. Після початку спільного обліку сформувати порівнювану базу: особисті витрати Олі плюс її частка спільних; окремо виміряти перший повний місяць Марка. Перерозподіл оренди, повернення боргів і відсутні виписки не вважати економією.

Під час пілоту обрати одну-дві керовані категорії й записати конкретну дію зі скорочення витрат. Щомісяця порівнювати повні періоди з однаковим складом витрат. Окупність фіксувати, коли накопичене підтверджене скорочення витрат перевищить фактичні витрати на трекер, переведені в PLN за фактичним курсом платежів. Гарантувати окупність до вимірювання результату не можна.

### Перевірки перед випуском

- Контрольні суми Олі за серпень і вересень збігаються до гроша.
- Працюють різні CSV, повторне завантаження, однакові покупки різних людей, зіставлення ручних записів і CSV, перекази між партнерами та округлення 50/50.
- Кожен банківський залишок узгоджується зі своєю випискою; зміни обліку проходять `uv run bean-check main.beancount` без повідомлень.
- На телефоні працюють три вкладки, вибір місяця, додавання витрати, показ помилки й повторне збереження без дублів.
- Підсумки враховують різні періоди покриття; відсутність даних не маскується нулем чи повним місяцем.
- Дані відновлюються з резервної копії; фінансові дані, ручні записи, резервні копії й секрети не потрапляють у Git; `data/` залишається лише для читання. Нові завантаження з телефона зберігаються поза `data/` у приватному сховищі.

Перед реалізацією актуалізувати обмеження версії 1 в `AGENT.md` і деталізувати цільову структуру обліку. Після кожного завершеного кроку оновлювати `PROGRESS.md`, виконувати відповідні перевірки й робити коміт українською.
