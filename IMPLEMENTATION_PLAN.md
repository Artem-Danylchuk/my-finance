# План збірки

Початкові кроки 1–5 нижче виконані. Наступна версія описана в розділі «Версія 2» наприкінці документа. Візуальний макет вкладок уже додано. У `shared.py` реалізовано й перевірено розрахунок часток і місячних компенсацій; підключення до обліку, звіту та серверні функції ще попереду.

Після кожного кроку оновлювати `PROGRESS.md` і робити коміт із коротким описом українською. Після змін в обліку обов’язково запускати `uv run bean-check main.beancount` і показувати результат; перевірка має пройти без повідомлень. Усі Python-команди виконувати через `uv run`, нових пакетів без дозволу не встановлювати. `data/` не змінювати.

## 3. Розрахувати місячні підсумки

**Зробити**
- Додати збережені запити нативною директивою `query`: витрати за категоріями й календарними місяцями; доходи, витрати та заощадження; витрати з тегом `#fixed` і без нього.
- Норму заощаджень рахувати як `(дохід − витрати) / дохід × 100%`; частки фіксованих і керованих витрат — від усіх витрат. Виводити витрати й доходи у зрозумілих додатних сумах, зберігаючи знак різниці заощаджень.

**Перевірити**
- Запустити `uv run bean-check main.beancount` і виконати запити через `uv run bean-query`.
- Незалежно звірити місячні підсумки з CSV: сума категорій дорівнює витратам; фіксовані плюс керовані дорівнюють витратам; дохід мінус витрати дорівнює заощадженням. Початкові 4 500 PLN не впливають на дохід.
- Перевірити від’ємні заощадження, нульовий дохід і нульові витрати на тимчасових даних поза `data/`; не ділити на нуль.

### Результат і межі

Розширити наявний трекер протягом 12 тижнів, працюючи кілька вечорів на тиждень. Зберегти Python, Beancount, правила категорій та оформлення звіту. Додати три вкладки, другий формат CSV і введення витрат із телефона. Користувачів рівно двоє; публічна реєстрація, застосунки для сторів, банківські API та інтеграції моделей у цю версію не входять.

Зараз результат — статичний HTML. Для спільного збереження даних із двох телефонів додати невеликий серверний шар до цього проєкту. Браузерний інтерфейс використовує наявні розрахунки, а не окрему копію обліку. Конкретний хостинг і потрібні пакети визначити на етапі технічної перевірки; цей план не встановлює пакети й не публікує фінансові дані.

### Три вкладки

| Вкладка | Що показує за обраний місяць |
| --- | --- |
| Загальна | Лише спільні оренда й продукти: сума за місяць, половина кожного, хто фактично оплатив, хто кому має компенсувати; особисті доходи, витрати та заощадження сюди не потрапляють |
| Оля | Її дохід, особисті витрати плюс її частка спільних, заощадження, фіксовані та змінні витрати; окремо фактичні оплати й сума взаєморозрахунків |
| Марко | Такі самі показники для Марка; поки його дані не додано — повідомлення «Даних ще немає», без вигаданих нулів |

Вибір місяця спільний для вкладок. Кнопка «Додати витрату» доступна на телефоні. Форма: дата, сума PLN, опис, категорія, особиста чи спільна; платник — поточний користувач. Для оренди й продуктів пропонувати 50/50 із можливістю позначити особисту покупку; решта за замовчуванням особиста. Два окремі входи: Оля бачить загальну й свою вкладку, Марко — загальну й свою. Вкладка іншого позначена як закрита без особистих сум. Сервер перевіряє права на кожне читання та зміну; чужі дані не передаються в HTML, відповіді API чи експорт. Приховування вкладки JavaScript не є захистом. Заборонено змінювати власника запиту, щоб отримати чужу виписку чи операції.

### Правила обліку

- Розрізняти платника та того, на кого припадає витрата. Спільну покупку показувати один раз у загальних витратах і по половині у персональних вкладках. Наприклад, Оля оплатила продукти на 100 PLN: загальні витрати 100 PLN, частка кожного 50 PLN, Марко має компенсувати Олі 50 PLN.
- Компенсація між ними зменшує борг, але не створює нового доходу чи витрати. Заощадження у персональній вкладці рахувати після розподілу спільних витрат; фактичну зміну банківського залишку показувати й звіряти окремо.
- Для непарної кількості грошів встановити один стабільний порядок округлення: частка Олі округлюється до гроша, частка Марка дорівнює залишку. Сума часток завжди дорівнює покупці.
- Дата переходу на спільний облік задається явно. Серпень і вересень Олі залишаються історією старої версії: змінні витрати 2 195,21 та 2 582,42 PLN. Не перерозподіляти їх заднім числом без підтвердження складу спільних покупок.
- Рахунки банків, власник, джерело й ідентифікатор операції зберігаються окремо. Однакові суми й описи в різних банках не є підставою видаляти операцію як дубль.
- Ручні записи зберігаються окремо від згенерованого файла операцій, щоб імпорт їх не стирав. При появі відповідного рядка CSV запропонувати зіставлення; після підтвердження це одна витрата з двома джерелами. Сумнівні збіги не об’єднувати автоматично.
- Дата покриття й початок обліку задаються для кожного користувача. Якщо дані одного неповні, загальний звіт явно неповний. Початковий залишок Марка брати з його виписки, не копіювати залишок Олі.
- Для двох одночасних записів передбачити безпечне збереження без втрати змін; повторне натискання «Зберегти» не створює другу витрату.

- Працюють різні CSV, повторне завантаження, однакові покупки різних людей, зіставлення ручних записів і CSV, перекази між партнерами та округлення 50/50.
- Кожен банківський залишок узгоджується зі своєю випискою; зміни обліку проходять `uv run bean-check main.beancount` без повідомлень.
- На телефоні працюють три вкладки, вибір місяця, додавання витрати, показ помилки й повторне збереження без дублів.
- Підсумки враховують різні періоди покриття; відсутність даних не маскується нулем чи повним місяцем.
- Загальна вкладка не розкриває особисті підсумки; підміна користувача чи ідентифікатора операції в запиті не відкриває чужих даних. Цю перевірку виконати для обох користувачів.
- Дані відновлюються з резервної копії; фінансові дані, ручні записи, резервні копії й секрети не потрапляють у Git; `data/` залишається лише для читання. Нові завантаження з телефона зберігаються поза `data/` у приватному сховищі.

Перед реалізацією актуалізувати обмеження версії 1 в `AGENT.md` і деталізувати цільову структуру обліку. Після кожного завершеного кроку оновлювати `PROGRESS.md`, виконувати відповідні перевірки й робити коміт українською.

### Пріоритети за списком із 18 фіч

Продуктове рішення: приватний браузерний трекер для двох у наявному проєкті; перша робоча версія — фічі 1–5. Нових платних інтеграцій у цьому обсязі не потрібно. Вибір сервера залишається в межах річного кошторису вище.

| 3 | Звіт на телефоні | Обов’язково: Марко не користується терміналом; ті самі розрахунки в адаптивному браузерному звіті |
